# Findings — MIV Stadt St.Gallen, first run

Generated by `scripts/run_miv_stadt.R`; full reports in `reports/`.

Both runs end in **FAIL**. Nothing below is a defect in the harness: each item
is a real divergence between `data/miv_original.parquet` and
`data/miv_transformed.parquet`, and the harness is reporting it.

The headline is that the **measure is clean**. `anzahl_fahrzeuge` is an exact
match across all **1'275'216** shared `(ort_id, datum, richtung, stunde)` keys,
with zero divergences — so `migrate_published_to_long()`'s wide→long pivot is
certified on this data. Everything that fails below fails for a different
reason.

## 1. `lnr` is a running number, not an identity — so it is not in the key

`miv_schema()$key` declares `c(lnr, ort_id, datum, richtung, stunde)`, but
`lnr` does not survive the transformation:

| | distinct `lnr` | rows | meaning |
| --- | --- | --- | --- |
| original | 4'018 | 54'478 | per-station counter; `(lnr, ort_id)` is unique |
| known-final | 53'158 | 1'275'792 | global 0…53'157 sequence over station-day-directions |

Keyed on `lnr`, only 2'864 of 54'478 station-days match and **every column
appears to fail**. The harness therefore uses
**`(ort_id, datum, richtung, stunde)`**, which is unique in both
(verified: `n_duplicated = 0` on both sides). This is the one key decision
taken on judgement — see the question at the end.

Consequence beyond this harness: `publish_miv()` and `update_miv()` match
provenance on `miv_schema()$key`. If `lnr` is renumbered between exports, that
join is unreliable and `erstpublikation` / `letzte_aktualisierung` will be
mis-assigned.

## 2. `kennzahl` — `derive_miv_cols()` disagrees with the published value

**This is the finding with the widest blast radius**, and it is invisible to
the migration step. It only surfaces in `configs/miv_stadt_derive.R`, which
recomputes the derived columns instead of passing them through:

| side | value |
| --- | --- |
| published / known-final | `Durchschnittlicher Tagesverkehr (DTV)**,**Durchschnittlicher Werktagsverkehr (DWV)` |
| `derive_miv_cols()` | `Durchschnittlicher Tagesverkehr (DTV)**;** Durchschnittlicher Werktagsverkehr (DWV)` |

Comma-no-space versus **semicolon-space**. One differing pair, **911'928 keys
affected** — 71% of the dataset. `arbeitstag` and `ort_richtung_id` recompute
correctly, so the rest of `derive_miv_cols()` is sound.

The next `publish_miv()` or `update_miv()` run from raw `.TXT` would silently
flip `kennzahl` on every `Werktage` row. Either `derive_miv_cols()` should emit
the separator the published data uses, or the published data needs a one-off
correction — that is your call, not the harness's.

## 3. `bezeichnung` is encoding-damaged on **both** sides

10 differing pairs after normalization (11 before — the harness's whitespace
collapsing correctly absorbed a double space in `St.Gallen Stadt  St.Fiden(neu)`).
They are not one defect but four:

**(a) Mojibake in the original — 4 names.** UTF-8 bytes stored as Latin-1.
Decoding `latin-1 → utf-8` reproduces the known-final *exactly*:

| ort_id | original | known-final |
| --- | --- | --- |
| 10908 | `St.Gallen Stadt FÃ¼rstenlstr. 57` | `St.Gallen Stadt Fürstenlstr. 57` |
| 10917 | `St.Gallen Stadt MÃ¼hlegg` | `St.Gallen Stadt Mühlegg` |
| 10920 | `St.Gallen Stadt MÃ¼ller-Fried.2` | `St.Gallen Stadt Müller-Fried.2` |
| 10927 | `St.Gallen Stadt SplÃ¼gen/Bachst` | `St.Gallen Stadt Splügen/Bachst` |

**A blanket repair would be wrong.** `ort_id 11282` carries
`St.Gallen Stadt Rosenb./Grüberg` as *correct* UTF-8 in the same column, so the
original mixes encodings and a column-wide `latin-1 → utf-8` pass would corrupt
that one.

**(b) Truncation at 30 characters in the original — 2 names, real data loss:**

| ort_id | original (decoded) | known-final | lost |
| --- | --- | --- | --- |
| 10929 | `St.Gallen Stadt Grossackers. 1` | `St.Gallen Stadt Grossackers. 14` | the `4` — a different address |
| 10935 | `St.Gallen Stadt Schwarzer Bäre` | `St.Gallen Stadt Schwarzer Bären` | the `n` |

Both land at exactly 30 characters. Truncation is not universal (the original
also holds 34- and 36-character names), so it looks like damage from one
particular export rather than a schema limit.

**(c) The known-final is the damaged side — 1 name.** `ort_id 10910`: the
original decodes to `St.Gallen Stadt Rötelibrücke`, while the known-final holds
`St.Gallen Stadt R?elibr?ke` — umlauts replaced by `?` *and* two characters
lost. Here the ground truth is worse than the input, so this one cannot be
fixed by trusting the known-final.

**(d) Genuine label differences — 3 names**, needing your decision on which
convention is correct:

| ort_id | original | known-final |
| --- | --- | --- |
| 10918 | `St.Gallen Stadt Gallusst./Webergasse` | `St.Gallen Gallusst./Webergasse` |
| 11253 | `St.Gallen Stadt Herisauer/Schranke` | `St.Gallen Herisauer/Schranke` |
| 10930 | `St.Gallen Stadt Flurhofstr. 68` | `Stadt SG Flurhofstr 68` |

This is the `changed` column that needs **your lookup table**. The harness
prints the pairs; it cannot assert which side is right, and says so.

## 4. The two files describe different station rosters

They are not input and output of a single transformation run. Beyond the shared
1'275'216 keys:

- **1'344 station-days (32'256 hourly rows) are in the original only** — two
  stations entirely: `ort_id 11282` *Rosenb./Grüberg* (1'316 station-days) and
  `ort_id 11539` *Turnerstrasse 29* (28 station-days, all with a missing
  `standort`).
- **24 station-days (576 hourly rows) are in the known-final only** — three
  stations on specific dates: `10921` Dufour/Winkelr (2024‑02‑17…19), `11257`
  St.Fiden(neu) (2024‑01‑02), `11261` Ob/Teufen.neu (2024‑01‑01).

A pure reshape cannot add or drop rows, so the known-final was not produced
from this original. See the question at the end.

## 5. `standort` is a WKB geo-point, and matches

Both files are GeoParquet: `standort` is binary WKB `Point`, not text. The
harness compares it as lowercase hex, never as a string. It matches on every
shared key (1'243'296 agreeing; 31'584 of the one-sided rows have a missing
`standort`, dropped before comparison on both sides alike).

## 6. The tracking columns agree — but that is coincidence, not evidence

`erstpublikation` and `letzte_aktualisierung` are both `2026-10-30` for all
1'275'792 known-final rows, which is also `miv_run_date()` today. They are
stamped at run time, not derived, so they are classed `new` and printed under
**uncovered gaps**: asserted by nothing. Re-running this on another day will
show them diverging, and that will not mean anything either.

## What is certified, and what is not

**Certified** — exact multiset equality over all 1'275'216 shared keys:
`anzahl_fahrzeuge`, `standort`, `wochentag`, `arbeitstag`, `ort_richtung_id`
(and `kennzahl` for the pass-through migration, though not when recomputed).

**Not certified:** `bezeichnung` (needs your lookup), `lnr` (regenerated,
asserted by nothing), `kennzahl` under recomputation, the 1'368 non-shared
station-days, and both tracking columns.

## Open questions

1. **The key.** The harness drops `lnr` from the grain key on the evidence
   above. Confirm, or name the key you want.
2. **The roster.** Were these two files produced from the same source export?
   If the known-final came from raw `.TXT` while the original is the currently
   published wide dataset, then this run is a *reconciliation* of two datasets,
   not a certification of the pipeline — and certifying the pipeline properly
   needs the raw `.TXT` inputs plus
   `detailplane-und-geokoordinaten-miv-zahlstellen-stadt-stgallen.csv`.
3. **`bezeichnung`.** Which side is authoritative, and is there a lookup table?
4. **`kennzahl`.** Should `derive_miv_cols()` switch to `,`, or should the
   published data be corrected to `; `?
